# Multiple Order handoff for Orang B

Apply `schema.sql` in the Supabase SQL Editor before testing the manual price flow. It is additive for an existing Pasokin database. The runtime schema has not been applied from this workspace.

## Shared fields

- `procurements.reference_code`: generated by Orang A on creation, format `PSK-XXXX`. Read it from the existing row for a confirmation summary.
- `procurements.negotiated_supplier_id`, `procurement_messages.supplier_id`: UUID foreign keys to `suppliers.supplier_uuid`.
- The older `suppliers.id` remains text for the existing dispatch, allocation, and payment code. Read `supplier_uuid` when storing either shared UUID field. The supplier API and `GET /api/procurements/:id` expose it.
- `procurements.manual_price`, `manual_unit`, and `manual_quantity` are nullable and ready for Orang B.
- `procurement_messages.message_type` is `negotiation` or `summary_confirmation`. `classified_as` must be null for every `summary_confirmation` row.

## Existing A interfaces

- `GET /api/procurements` returns active cards. `GET /api/procurements/:id` returns a procurement with scoped `allocations`, `dispatched_suppliers`, and `messages`.
- `procurementsStore.get(id)`, `setStatus(id, status)`, `supplierUuid(legacyId)`, and `addMessage({ procurementId, supplierId, messageType, direction, rawText })` are available on the backend.
- The WhatsApp webhook routes a reply with its `PSK-XXXX` code to the matching procurement and sender. While the procurement is `awaiting_summary_confirmation`, it stores `message_type='summary_confirmation'`, `direction='inbound'`, and skips AI classification. The buyer decision UI and confirm/reject endpoints belong to Orang B.

The standalone dummy reference `PSK-TEST` fits the same format. Use an existing `suppliers.supplier_uuid` for `negotiated_supplier_id`.
